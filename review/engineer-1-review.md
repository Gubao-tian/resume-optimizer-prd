# 技术可行性评审意见（后端 / 全栈视角）

## 1. 需求理解与歧义
我的理解：V1.0 是一个单页工具——用户输入一条简历经历原文 + 目标岗位 JD，30 秒内返回四要素（结构化改写、逐处修改对照表、JD 关键词提示、缺失信息反问），零虚构、零保存、免注册。

歧义与缺口：①「改写与追问」交互流未定义——是先反问再改写，还是一次性输出+追问清单？两种 Prompt 设计差异很大；②四要素输出格式（表格/列表/JSON）未约定，直接影响前端工作量与 LLM 输出稳定性；③隐含假设 JD 为纯文本，超长 JD 的截断规则缺失；④「AI 味」无自动判据，只能靠 Prompt 负面词清单+人工抽检。

## 2. 技术方案
- 前端：静态单页（React/Vite），GitHub Pages 部署，零存储。
- 后端：Serverless 函数（Node/Python，Vercel/CF Workers）仅作 LLM API 代理，隐藏 API Key，限流防刷。
- LLM 选型：国产 API（DeepSeek 级），单次成本约 0.01 元，满足 ≤10 元红线；GPT-4 贵且国内访问不稳，不选。
- Prompt 组织：System 锁定角色+负面词清单+四要素 JSON Schema（字段强制），User 装载经历+JD；temperature=0.3 保稳定。
- 数据流：浏览器 → Serverless → LLM，请求即走即弃，内存不落盘、不记正文日志，从架构上满足「不保存简历内容」。
- 部署：全免费档起步，成本上限靠限流+简单验证码控制。

## 3. 工作量评估（两人合计约 12-15 人日）
Prompt 设计与调优（核心难点）3-4｜Serverless+LLM 对接 2-3｜前端与四要素展示 2-3｜回归测试+时效压测 2-3｜部署与文档 1-2。

## 4. 风险与约束
- 幻觉（最大风险）：Prompt 强制「新增信息必须可溯源，否则放入反问」；后置脚本校验改写中数字须出现于原文。
- 输出不稳定：JSON Schema+低温度；建 10 条固定回归用例人工比对。
- 30 秒时效：国产模型首 token 1-3 秒、800 字生成约 10-20 秒，有余量；设 30 秒超时友好降级。
- 成本：单次约 0.01 元，免费额度够演示；防刷是成本控制关键。
- 隐私：免登录+不落盘可达成，页面须明示「输入仅用于本次生成，不存储」。
- 范围建议：必须做——四要素输出、隐私声明、限流；建议放 V1.1——复制导出、历史记录、超长输入支持。

## 5. 验收标准补充（工程可测）
- P95 端到端时延 ≤30 秒（压测工具实测，非主观感受）
- 10 条回归用例 100% 返回合法四要素 JSON（无字段缺失）
- 溯源脚本校验：改写中数字 100% 可回溯原文或反问清单
- 负面词（赋能/抓手/闭环等）出现次数=0（脚本扫描）
- 单 IP 超频返回 429+友好提示；空输入/5000 字/特殊字符不崩溃

## 6. 明确结论：可行，但有条件
技术可行，V1.0 范围无需调整，可冻结。条件清单：
1. Prompt 迭代预留 3-4 人日，质量不达标时砍周边功能保核心；
2. 输出强制 JSON Schema+低温度，换取结构化与稳定性；
3. API Key 必须走 Serverless 代理，不上前端；
4. 确认国产 LLM 选型（建议 DeepSeek 级 API）后冻结范围。
