## 二、执行摘要



简历润笔是一款面向求职者的简历单条经历改写工具：用户粘贴一条简历经历与目标岗位 JD，产品在 30 秒内返回四项输出——结构化改写文案、逐处修改对照、岗位关键词提示、缺失信息反问。产品秉持"帮用户挖出经历的价值，绝不编造经历"的原则，以零虚构、无 AI 味、不存数据为三条不可逾越的红线。



V1.0 由五人团队（1 名产品经理、2 名用户代表、2 名研发工程师）经需求调研与技术可行性评审定义，唯一核心功能为「JD 对照的单条经历改写」，研发结论为"可行但有条件"，条件已全部纳入本文档。交付形态为 GitHub 上的可运行 Web 应用（静态前端 + Serverless 代理 + 国产大模型 API）与本文档。



## 三、目标与非目标



### 3.1 产品目标



1. 帮助两类目标用户（零实习应届生、转行跳槽者）把真实经历翻译成目标岗位看得懂、经得起面试追问的语言；

2. 单次改写 30 秒内（P95）给出可直接使用的结构化结果；

3. 守住三条产品红线：零虚构、无 AI 味、不存用户简历数据。



### 3.2 非目标（V1.0 明确不做）



简历排版模板、PDF 导出、多版本管理、投递追踪、全文简历评分、岗位百科、账号系统、历史记录、无 JD 场景支持。以上列入版本规划（见第十四章），V1.0 不投入资源。



### 3.3 设计原则



1. **挖而不编**：所有新增信息必须可溯源至用户输入；信息不足时留白反问，绝不编造；

2. **单条闭环**：V1.0 只把"单条经历改写"一件事做到位，拒绝功能铺开；

3. **可解释**：每处修改必须给出理由，让用户看得懂、敢采用、能复述；

4. **即走即弃**：隐私靠设计保证——免注册、不落盘、页面明示；

5. **30 秒承诺**：时效是体验的一部分，超时必须有降级，不允许无限等待。



## 四、背景与问题陈述



### 4.1 背景



求职季中，简历筛选普遍经过机器筛选（ATS）与 HR 人工阅读两道关口，简历内容的目标岗位匹配度直接决定能否进入面试。与此同时，通用大模型已普及，但用户调研显示：通用对话式 AI 输出存在"AI 味重、不懂岗位语境、可能虚构经历"三大问题，用户不敢直接采用；人工润色价格高、周期长且有隐私顾虑。市场上缺少一款"懂岗位语境、只挖不编、低价即时"的单点工具。



### 4.2 问题陈述



两类典型用户被困在同一个环节——**有真实经历，但写不出价值**：



- 零实习应届生：简历只有课程项目与校园经历，通篇"负责 XX"，不懂 HR 与 ATS 看重什么关键词，想包装又怕面试追问穿帮；

- 转行跳槽者：经历真实（投放、活动、报表）但无数据成果，不懂哪些旧经验对目标岗位有价值，怀疑简历在 ATS 关键词过滤阶段就被淘汰。



## 五、用户调研



### 5.1 调研方法与团队



调研由产品经理组织，五位团队成员构成：产品经理 1 名（需求分析与归纳）、用户代表 2 名（User A、User B，分别代表两类目标人群）、研发工程师 2 名（技术可行性评审）。调研围绕五个问题展开访谈，研发随后参与评审。本章记录各方发言要点与归纳结论，完整记录存档于 GitHub 仓库。



### 5.2 调研五问



#### 5.2.1 用户是谁？有什么真实痛点？



**User A（2027 届应届生）**：本人为计算机专业本科生，找产品运营 / 产品经理实习与校招，已海投 80 余份简历，面试邀约率约 5%。三个具体痛点：一是写出来像岗位说明书不像成果，HR 十秒扫完抓不到重点；二是不知道 HR 和 ATS 先看什么关键词，只能一份简历海投所有岗位；三是课程项目想包装又不敢包装，怕面试官追问"这个数据哪来的"时穿帮。



**User B（28 岁，3 年市场专员，转行中）**：简历里有真实内容（活动策划、信息流投放、周报月报），但通篇"负责 XX、参与 XX"，零数据成果；不确定哪些旧经验对目标岗位有价值；投递后经常无回音，怀疑简历在 ATS 筛选阶段就被关键词过滤。



**归纳**：目标用户分两类（见第六章画像），共同痛点为内容不会写、不懂岗位语境、现有工具各有硬伤。



#### 5.2.2 为什么现有产品不能很好地解决问题？



**User A**：简历模板网站只换排版不改内容，问题在内容不在皮；通用大模型输出"主导设计并实现了 XX 系统，显著提升团队协作效率"这类表述，AI 味重，不敢往简历上抄，且不懂产品岗筛选逻辑；人工润色报价 80 至 300 元，学生价格敏感，还要把真实简历发给陌生客服，怕经历被夸大、信息被留存。



**User B**：模板网站只解决排版，内容还得自己写，而自己是没内容可写；通用大模型改完满篇"赋能、抓手、闭环"，还把经历改得面目全非，面试一追问细节就虚；人工润色一问几百块、沟通来回好几天，而自己下周就要投。



**归纳（竞品缺口）**：



| 现有方案 | 能解决 | 不能解决 |

|----------|--------|----------|

| 简历模板网站 | 排版美观 | 内容改写、岗位关键词匹配 |

| 通用大模型对话 | 泛泛润色 | 岗位语境、AI 味、经历虚构、结构化输出 |

| 人工润色服务 | 一定程度的定制化 | 价格高（80 至 300 元）、周期长（数天）、隐私顾虑 |



#### 5.2.3 我们的产品准备解决什么问题？



两位用户表述高度一致：要一个"帮我挖"而不是"帮我编"的工具——把真实经历翻译成目标岗位看得懂、经得起面试追问的语言。



**产品定位（一句话）**：粘贴一条简历经历加目标岗位 JD，30 秒内把它"翻译"成有成果、有岗位关键词、经得起面试追问的描述——帮用户挖出经历的价值，绝不编造经历。



**明确不解决**：简历排版（免费模板已足够）、投递渠道。



#### 5.2.4 V1.0 最重要的功能是什么？



**User A 选择单条经历改写**：输入一条原文（如"负责 XX 系统的需求分析与功能设计"），输出改好的描述、改了哪里、为什么这么改。理由：投一个岗位就要改一轮描述，这是最高频动作；先把一条改好，再谈别的。期望一次只改一条、逐句对照。



**User B 选择 JD 对照的逐条改写**：上传简历加目标 JD，逐条把"负责 XX"改写成"动作 + 方法 + 结果"，并标注经历对应目标岗位的哪项能力；缺数字的地方要反问追问，而不是替用户编。理由：最痛的不是排版也不是没经历，而是写不出价值加不知道对方要什么；多版本管理、PDF 导出、投递追踪都是锦上添花。



**产品经理决策**：两位用户的选择本质相同，均指向同一核心能力。**V1.0 唯一核心功能定为「JD 对照的单条经历改写」**，并将 User B 提出的"经历与岗位能力对应"吸收为其中的关键词提示要素。



#### 5.2.5 如何判断功能已经满足需求？



**User A 四条标准**：改动可解释，每处修改都说明为什么；零虚构，新增内容必须出自己给的原文；提示哪些产品岗关键词该保留；10 分钟内能独立改完一条经历。



**User B 四条标准**：每条经历都有动作 + 方法 + 结果；能对着改写后的简历说出每条真实细节，面试追问不虚；用改写版投递一周，面试邀约从 0 到有；全文无 AI 味。此外，当用户反馈"这条不对，当时其实是 XX"时，产品要能据此修改。



**归纳**：整理为分层验收标准（见第九章），其中"零虚构"与"无 AI 味"为一票否决项。

## 七、产品方案



### 7.1 方案概述



V1.0 为一个单页 Web 应用：左侧输入区（经历原文 + 目标 JD），右侧结果区（四张卡片）。用户提交后，后端经 Serverless 代理调用大模型，返回结构化四要素结果。产品不提供账号体系，不存储任何输入内容。



### 7.2 功能需求



| 编号 | 需求 | 优先级 | 验收标准 |

|------|------|--------|----------|

| FR-1 | 经历原文输入：支持粘贴单条经历文本，上限 300 字，实时字数提示 | P0 | 输入不超限可正常提交；超限给出明确提示；空输入给出引导文案，不崩溃 |

| FR-2 | 目标 JD 输入：支持粘贴 JD 文本，上限 2000 字，输入区可折叠 | P0 | JD 为必填项，缺失时引导用户粘贴并说明原因 |

| FR-3 | 单条经历改写（核心）：基于原文与 JD 生成"动作 + 方法 + 结果"结构的改写描述 | P0 | 30 秒内（P95）返回；结构完整；零虚构（见第九章 Q1） |

| FR-4 | 逐处修改对照表：以片段级高亮展示原文片段、改后片段与修改理由 | P0 | 每处修改均带理由，理由缺失率 0；用户可逐条核对 |

| FR-5 | 岗位关键词提示：区分"已保留"与"可补充"两类标签，关键词来源于 JD | P0 | 可补充项明确标注"建议确认后自行添加"，不写入改写文案 |

| FR-6 | 缺失信息反问：列出缺失的数字与细节追问，可跳过；用户补充后可重新生成 | P0 | 反问不阻塞首版输出；补充后重新生成功能可用 |

| FR-7 | 一键复制：复制改写后的经历描述 | P0 | 点击即写入剪贴板，并有成功反馈 |

| FR-8 | 隐私声明：首次访问展示数据处理说明（即走即弃、不落盘） | P0 | 声明可见且可随时重新查看 |

| FR-9 | 频率限制：超频请求返回 429 与友好提示 | P0 | 压测验证触发限流，正常使用不受影响 |

| FR-10 | 加载与降级：等待过程有明确进度反馈；超过 30 秒未返回时给出重试引导 | P1 | 无静默失败；降级路径可走通 |



### 7.3 用户流程



**主流程**：粘贴经历原文与目标 JD → 点击提交 → 30 秒内返回四要素首版 → 用户阅读对照表与关键词提示 →（可选）回答反问补充细节并重新生成 → 一键复制改写结果。



**异常流程**：输入不合法（空、超限、特殊字符）→ 页面内引导提示；模型超时 → 提示重试；模型返回结构损坏 → 自动重试一次，仍失败则给出友好错误页。



### 7.4 边界与异常处理



| 场景 | 处理方式 |

|------|----------|

| 经历输入为空 | 输入框下方提示"请粘贴一条简历经历"，阻止提交 |

| 经历超过 300 字 | 实时字数提示变红，引导拆分多条 |

| JD 为空 | 提示"请粘贴目标岗位 JD，否则无法进行岗位对照改写" |

| JD 超过 2000 字 | 提示精简至岗位职责与任职要求部分 |

| 特殊字符与超长文本 | 输入 sanitize 处理，不崩溃、不报错栈 |
| 仅含标点/符号/emoji | 输入层拦为 400「仅标点、符号或表情无法改写」（见 Issue #22） |
| 仅含虚词（如「与、和」） | 输入层拦为 400「仅有标点或虚词无法改写」（见 Issue #34） |

| 模型响应超过 30 秒 | 前端展示等待状态，超时后引导重试 |

| 模型返回非法结构 | 自动重试一次；仍失败则展示友好错误与重试按钮 |

| 触发频率限制 | 返回 429 与"已达当前网络出口的用量上限（校园网/公司网下与同网用户合并计算），请稍后再试"提示（见 Issue #24） |



## 八、技术方案



两位研发工程师已完成评审，结论均为"可行但有条件"，条件已全部吸收进本文档（输入长度上限、反问时序、关键词仅提示不写入、回归集评分口径）。



### 8.1 架构与选型（研发工程师 1，后端 / 全栈视角）



| 层 | 选型 | 理由 |

|----|------|------|

| 前端 | React 加 Vite 构建静态单页，部署 Vercel（同域单项目） | 免服务器、零运维，前端产物与 Serverless 同源部署 |

| 后端 | Serverless 函数（Node 或 Python）仅作 LLM 调用代理 | 隐藏 API Key、限流防刷 |

| 模型 | DeepSeek `deepseek-flash`（OpenAI 兼容协议，可替换 GLM 等） | 中文简历语境好、单次成本约 0.01 元、响应快；思考模式默认关闭使 temperature 生效 |

| Prompt | 系统角色加负面词清单加四要素 JSON Schema，温度参数 0.3 | 强制结构化输出、抑制幻觉 |

| 数据流 | 即走即弃，不落盘、不记录正文日志 | 满足隐私红线 |



### 8.2 Prompt 与输出质量控制（研发工程师 2，前端 / AI 应用视角）



1. Prompt 分三层：系统角色（只翻译不创作）、硬规则（禁止新增原文没有的事实与数字，缺数字写"待补充"并同步进反问）、固定 JSON Schema；

2. 输出后校验三道：敏感词表（赋能、抓手、闭环等）命中即重写或标红；虚构检测（抽取输出中的数字与专有名词，与原文及用户补充比对，新增即拦截）；关键词保留率实时计算并展示。



### 8.3 隐私与安全



1. 免注册、免登录，不收集联系方式；

2. 用户输入即走即弃：不写数据库、不记正文日志，仅记录脱敏的调用指标（耗时、结果结构合法性）；

3. 页面明示数据处理方式，接受用户监督；

4. API Key 仅存于 Serverless 环境变量，不下发前端。



### 8.4 性能与成本



1. 服务等级目标（SLO）：P95 端到端时延不超过 30 秒；可用性目标 99%（周末项目按尽力而为记录）；

2. 单次模型调用成本约 0.01 元，配合频率限制与验证码控制成本上限；

3. 超时降级：超过 30 秒未返回即引导重试，不无限等待。



### 8.5 工作量评估



V1.0 总计 12 至 15 人日（2 名工程师合计）：Prompt 与输出控制 3 至 4 人日、Serverless 与 LLM 对接 2 至 3 人日、前端开发 2 至 3 人日、回归测试与压测 2 至 3 人日、部署与文档 1 至 2 人日。



## 九、验收标准（DoD）



### 9.1 功能验收



1. F1：输入一条经历（不超过 300 字）与 JD（不超过 2000 字），30 秒内（P95）返回四要素，无空区块；

2. F2：四要素齐全，逐处对照表中每处修改均带修改理由；

3. F3：反问可跳过，补充后重新生成功能可用；

4. F4：一键复制功能在主流浏览器可用。



### 9.2 质量验收



1. Q1：零虚构——改写结果中的数字与专有名词 100% 可溯源至用户原文或用户补充（脚本校验），**一票否决**；

2. Q2：无 AI 味——负面词表扫描 0 命中，**一票否决**；

3. Q3：稳定性——同一输入连续 3 次运行，输出结构完整、结果可用性稳定。



### 9.3 用户验收



1. U1：User A 使用 3 条真实经历（课程项目、外联、兼职）逐条测试，"可直接使用或仅微调"的比例不低于三分之二；【状态：Mock 演示模式下无法判定，需 T9 真实模型实测后重出，见「研发与测试交付记录」】

2. U2：User B 使用真实简历与目标 JD 测试，能逐条复述每条经历的真实细节，对关键词对应关系的认可度不低于 80%；

3. U3：12 至 15 条固定样本回归集评分均分不低于 4 分（5 分制），且虚构项为 0。



### 9.4 工程验收



1. E1：10 条回归用例 100% 返回合法结构化输出；

2. E2：压测实测 P95 端到端时延不超过 30 秒；

3. E3：第七章 7.4 节所列异常场景全部给出友好引导且不崩溃；超频调用返回 429 与明确提示。

## 十六、研发与测试交付记录（V1.0 实际交付）

> 本章为 V1.1 新增：PRD 最初以「范围待冻结」收尾，本节记录研发实际交付结果，
> 使 PRD 与产品真实状态对齐，而非停留在规划阶段。

### 16.1 交付物

- **产品仓库**：https://github.com/Gubao-tian/resumepolish（public，MIT 协议）
- **Release**：v1.0.0（含完整 release notes、已知限制、17 个 PR 变更日志）
- **技术栈落地**：React 18 + Vite 5 前端，Vercel Serverless 函数，全仓 ESM JavaScript（零 TypeScript）
- **模型落地**：DeepSeek `deepseek-flash`（OpenAI 兼容协议，可替换）；Mock 为一等公民，无 Key 自动进入演示模式

### 16.2 质量证据

- **测试**：197 项 `node:test` 单测全绿（Node 20 与 Node 22 双环境），覆盖输入/输出七道校验、限流、Mock 行为、上游请求体、`.env` 加载器、前端契约适配
- **CI 门禁**：每次 push / PR 自动执行 `npm ci` + `npm test` + `npm run build`（Linux + Node 20）
- **真实调用分支**：此前全量测试仅覆盖 Mock 路径，后以本地假上游补上真实分支端到端验证（7/7 通过，覆盖 ok / 5xx / 401 / 非 JSON / 超时 / 数字放大 / 空 content）

### 16.3 Bug 管理闭环（真实流程）

按「Issue Submitted → Triage → Reproduce → Fix → Code Review → Test → User Acceptance → Closed」流程处理，共 44 个 PR / Issue，完整闭环案例为 **Issue #22**（纯标点输入 500）：

| 阶段 | 执行 |
|------|------|
| Issue Submitted | User A 提交纯标点输入返回 500（#22） |
| Triage | PM 定级 P1（真实链路白烧两次 LLM 调用） |
| Reproduce | 研发独立复现并定位根因（输入/输出「空」口径不一致） |
| Fix | PR #25（输入/输出校验统一「空」口径） |
| Code Review | 研发 review，反哺出 #34–#38 五个后续缺陷 |
| Test | 测试数 166 → 197，全绿 |
| User Acceptance | User A / User B 逐条验收，公开评论留痕 |
| Closed | 关闭 |

### 16.4 已知限制（如实记录，不粉饰）

1. **真实模型实测（T9）未完成**：真实延迟 P50/P95、单次成本、JSON 首 Try 合法率、真实输出质量——需用户提供 API Key 后实测；当前选型是桌面推演 + 真实分支链路验证，**非实测结论**
2. **「关闭 thinking 不损失质量」未证实**：仅有官方参数语义支撑，无实测证据，列为 T9 必测 A/B 项
3. **真实样本回归集（T10）待补**：需 User A（课程项目类）、User B（投放/活动类）各 ≥3 条真实样本
4. **限流为单实例内存态**：多实例部署下不共享计数；按 IP 计数在校园网/公司网 NAT 下会误伤同网用户（Issue #24，待产品决策）
5. **U1 验收在 Mock 下无法判定**：改写文案为确定性模板，非真实模型推理，真实结论须待 T9

### 16.5 遗留台账（后续处理，不阻塞 V1.0）

- 能力章节仅一句超长中文职责时，关键词 fallback 可能产出「岗位职责：负」类残片（与「中文长 token 参与打分」同属结构性待办）
- 「无宾语纯动词」（如「跟踪」）不作为关键词——需结构性改动（长 token 也参与打分）
- 限流粒度 / 阈值待 T9 真实用量数据后产品决策
